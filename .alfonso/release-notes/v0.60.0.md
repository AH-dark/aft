# AFT 0.60.0 (unreleased)

## Changed

- Upgrading invalidates the cached call graph and the stored call-graph data used by checkout views for every project. Each project rebuilds them once when next needed, so its first graph-dependent request may take longer while the rebuild finishes.

- Access policy: sandboxed worker shells can no longer reach a shared sccache server on macOS; Linux reports this protection as unenforced.

- Sessions now have approval modes. Full access is the default for primary agents (heads) for now; `ask` and `read-only` remain available. In `ask` mode, primary agents ask the user for permission before accessing files outside their project. macOS permission denials raise a fix-it card with steps for System Settings.

- GitHub bot comments from agent sessions are sent only under the session's agent scope. AFT no longer mints agent assertions from prefrontal. A bot write from a session that isn't bound under its agent's scope is refused before anything is sent, with `bot_write_requires_scope`; restarting the host session binds it scoped. The `gh` shim's check of which bot is bound to a repository, run before every bot write, now reads plexus's binding list without an agent assertion.
- AFT declares call modes through subc-protocol 0.31: classic keeps every existing tool, codemode serves the head catalog with direct-call parity, and flow serves only `read`, `grep`, `glob`, `aft_search`, `aft_outline`, `aft_zoom` and `aft_callgraph`. Codemode bash refuses background and PTY work, clamps its timeout to the run deadline (refusing a missing deadline), and kills its process group once the run scope is confirmed ended. Flow refuses shell, writes and `aft_inspect` as `call_mode_unsupported`; inspect can execute repository build scripts. Unknown modes are also refused as `call_mode_unsupported`.

- Views: an incremental call-graph update could store a different result than a full build when two references in a file shared an ordinal. The materialization version moves from 9 to 10, so every view rebuilds its call graph once, on its next publication after upgrading.

- A bash command that finishes within its call now ends its reply with a `[task …]` line naming its task; for a `runon` command the line also names its build-server job.

- `bash_status` and `bash_watch` on a `runon` task now report, while it is queued, how long it has waited on the build server and its queue position; once it starts, when the runner will stop it.

- When a waiting bash call is cancelled (client cancel, lost connection, restart) while its command keeps running, the reply to the session's next bash call names that still-running command's task once, and the command's completion notice is no longer lost.

- A `runon` refused because its workdir is outside this session's checkout now names the workdir and the session's checkout, and says whether the workdir is in no checkout or in another repository.

- Views: a linked git worktree no longer builds its call graph when it binds or after edits. While its files match the main checkout's published view, `aft_callgraph`, zoom's call-graph annotations and `aft_inspect`'s dead-code and other Tier-2 categories answer from the main checkout's graph, with the worktree's own paths. The first such query after the worktree changes (an edit, commit or checkout) reports the graph as building and starts the build, seeded from the main checkout as before; from then on later edits keep it current. A worktree that never queries the call graph never builds one, even when an earlier run already built one for it: until a query in the current process needs the graph, its publications leave the graph unbuilt instead of updating the old one. Main checkouts still build eagerly. Stored formats are unchanged; a worktree generation published before its graph is built simply has no `derived-<generation>.sqlite` file.

- Maintainers: main, train and PR CI run native E2E with optimized non-LTO `stage` binaries; releases require E2E of shipped fat-LTO `release` binaries and reuse those checksum-verified bytes for macOS ARM64, Windows x64 and Linux x64.

## Fixed

- Dead-code findings now recognize Rust static values that are read and calls made through a used private type's trait implementation, including the functions those paths call. Rust declarations compiled only for tests are left out of production findings. Test imports whose query string changes while their source path stays fixed are now recognized as test-only uses rather than unused exports.

- Workers restored after interruption retain their remote runner and saved launch settings without needing another tool catalog fetch.

- OpenCode and Pi primary agent sessions retain the scope supplied by core, which identifies the agent allowed to send GitHub bot writes, on both tool and background-event routes after an AFT restart or bridge reconnect. Temporary module-reload refusals no longer permanently downgrade a session to unscoped, and background routes now upgrade when a scope lookup recovers, even if the tool route is gone or a fallback bind is still opening. The `gh` shim now attributes `bot_write_requires_scope` to AFT and explains that the session's tool route needs its core scope, rather than reporting an unknown Plexus refusal.
- Worker bash commands now refuse synthetic CPU load hidden behind `exec`, `nohup`, `setsid`, `stdbuf`, `time`, or `caffeinate`, including nested wrappers and background subshells. Small, bounded `yes | head` pipelines remain allowed.
- The synthetic-load refusal now states that shared machines, local or remote, are off limits and asks for deterministic proof instead of suggesting the remote runner, where the same refusal applies.
- Views: disk-limit checks of different repositories no longer run all at once. One check runs at a time across the daemon, and the others wait their turn instead of being dropped. Before, each repository's check started its own thread, so a daemon with many repositories ran about 20 at once. They all walked the same views folder and every one of them hit its 60-second limit. When a new view is refused over the hard limit, the message now says whether its eviction pass started or is queued behind another repository's check.
- Views: a disk-limit check that ran out of time recorded every view it had not measured as 0 bytes. Admission of new views then read the repository as empty and never refused one, and the log showed `view_store_bytes=63181441->0`. A view or family store the check could not measure to the end now keeps its last recorded size, and the record is marked incomplete. The log prints an unmeasured total as `unknown`, and an admission refusal says when the last measurement did not finish.
- Configure no longer walks the whole project on the bind path to decide which language servers apply. That walk now runs on its own thread after the reply. On a large or busy new checkout it had held configure's `state_commit` phase for 11 to 21 seconds, so route binds missed their deadline and worker launches failed. Until the walk finishes, the status bar shows diagnostics as pending for a new root. The "configure prefix slow" log line now breaks `state_commit` into named steps, for example `state_commit=40ms(database_runtime=0ms,lsp_search_paths=0ms,config_publish=1ms,...)`.
- `aft_inspect` now waits for that background language-server walk before it answers, for up to half of its remaining request budget. Before, an inspect that ran right after configure could leave the status bar reading diagnostics as pending, even when a language server was known to be missing. If the wait runs out, the inspect still answers for what it analyzed, but its reply is PARTIAL: the header reads `diagnostics unknown: language-server applicability: applicability_walk_running: ...; retry aft_inspect.`, the diagnostics totals are left unknown, and the diagnostics summary and the reply's gaps carry an `applicability_pending` gap. The status reply then shows `diagnostics: pending` with `diagnostics_reason: applicability_walk_running`. The status reply now gives a reason whenever diagnostics are pending: `applicability_walk_running`, `applicability_unknown` (no walk has recorded a result), or `producer_reports_pending` (a language server has not reported yet).
- The daemon's health rollup thread does less work on each 3-second pass. Before, every views-on repository's path-status database was opened, queried and closed on every pass, and closing it checkpointed its write-ahead log. Now the database is read again only when its files change, or every 30 seconds at most. Each repository's in-memory indexes are now walked once per pass for the memory figures instead of twice. On a test view, 50 health reads went from 50 database opens (5.7 ms) to 1 (0.4 ms).

- On OpenCode 2, AFT's `bash` and `apply_patch` now register as `shell` and `patch`, so OpenCode 2 renders them natively; each session rebuilds its prompt cache once (#406, thanks @null-axiom).
- Ordinary local Unix piped shells now save their PID before executing user commands; the wrapper waits for AFT to confirm that write before running user code. If AFT dies before that confirmation, the command never starts and recovery reports Failed/"spawn aborted" without a command exit code. On rollback the task remains failed; an older AFT version may show only its task id for a Starting record (as before this release), or `[exit code: -2147483648]` if the record had advanced past Starting. Remote refusal followed by local execution keeps its separate persisted marker preventing a second execution after restart.

## Storage

- `aft.db` moves to schema 16, which adds the `access_scopes`, `access_grants`, `access_launch_params` and `access_materialized` tables for permission grants. An older AFT refuses a schema-16 database. To roll back past this release, stop AFT, then in one transaction drop those four tables and set `schema_version` to 15. Before restarting the older binary, also lower only the `aft.db` entry in the storage root's `reader-floor.json` to 15; leave every other store's floor unchanged. The database downgrade alone does not lower that independent reader floor.

- Inspect stores per-file duplicate-code records as compact tuples instead of JSON objects and avoids unused in-memory copies; cache format 40 rejects cached project-analysis results from older versions and rebuilds old duplicate records on the next analysis to match the new storage format (groups, ordering and text are unchanged).

- `aft.db` moves to schema 17, which adds the `access_asks` table: permission asks that stamped Alfonso workers left open with Cingulate, with the consent call key each was first sent under. An older AFT refuses a schema-17 database. To roll back past this release, stop AFT, then in one transaction drop `access_asks` and set `schema_version` to 16. Before restarting the older binary, also lower only the `aft.db` entry in the storage root's `reader-floor.json` to 16; leave every other store's floor unchanged. The database downgrade alone does not lower that independent reader floor. This discards every open ask; a worker that retries its call asks again. Continue with the schema 16 steps above to go back further.

- `aft.db` moves to schema 18, which adds `access_modes`, `access_scope_agents` and `macos_permission_cards` for approval modes and macOS fix-it card tracking. An older AFT refuses a schema-18 database. To roll back past this release, stop AFT, then in one transaction drop those three tables and set `schema_version` to 17. Before restarting the older binary, also lower only the `aft.db` entry in the storage root's `reader-floor.json` to 17; leave every other store's floor unchanged. The database downgrade alone does not lower that independent reader floor. Approval modes fall back to the default, and open macOS fix-it cards are forgotten locally; Cingulate keeps its own copy. To return to schema 16 or earlier, continue with the schema 17 rollback steps above.

- Storage retention reclaims checkout view folders (`views/<scope>`) faster. Caches whose checkout is gone and past its grace are now cleaned on the next pass, instead of waiting for the walk over every cache to reach them, which could take about two days. A deleted linked worktree (a worker checkout) no longer keeps its index data for 24 hours: it is removed on the first pass once 10 minutes have passed since its last bind. The 10 minutes let a session that bound just before deletion finish, and let a checkout recreated at the same path rebind first. Every other checkout, including a linked worktree whose binding was recorded before 0.59, still keeps 7 days. A view folder that no family registry lists and no binding records is removed once it has gone an hour without being observed or changed, if nothing pins it, reads it or locks it. Before, it waited a week. If a registry or another needed fact cannot be read, the folder is kept and counted under `skipped_unknown`. A binding record written by a release before 0.59, which did not record whether its checkout was a linked worktree, is now upgraded while its checkout still exists. The inspect projection lookup no longer creates an empty view folder for a checkout that has none. Each pass report adds `due_keys` (keys past their grace that still have caches; a key identifies one checkout's caches, or the caches shared by one repository), `due_first` (what the pass examined, skipped and removed for those keys before the walk resumed), `orphan_views` (the same counts for orphan view folders), `skipped_unknown` and `upgraded_bindings`.
